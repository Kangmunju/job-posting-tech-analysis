
# 데이터 접근 및 수집 기록

## 1. 데이터 수집 개요

본 프로젝트에서는 IT 직무별 요구 기술을 분석하기 위해 원티드(Wanted)의 채용공고 데이터를 수집하였다.

채용공고에 포함된 직무명, 자격요건, 주요업무, 우대사항 등의 텍스트를 활용하여 직무별 핵심 기술과 차별화 기술, 기술 간 공동출현 관계를 분석하였다.

### 1.1 데이터 출처

- 플랫폼: 원티드(Wanted)
- 데이터 유형: IT 직무 채용공고
- 접근 방식: 별도 API 키 없이 접근 가능한 채용공고 API 활용
- 수집 대상: 데이터 분석가, 데이터 엔지니어, 데이터 사이언티스트, 백엔드, 프론트엔드 관련 카테고리
- 중복 제거 후 수집 공고 수: 1,273건
- 재게시 공고 정리 후 공고 수: 1,267건
- 최종 분석 공고 수: 705건

### 1.2 데이터 활용 목적

수집한 채용공고는 다음 분석에 활용하였다.

- 직무별 주요 요구 기술의 등장률 분석
- TF-IDF를 활용한 직무별 특징적인 기술 분석
- 공동출현 횟수 및 Jaccard 유사도를 활용한 기술 조합 분석
- LLM 요구 현황, 경력별 기술 수, 직무 간 유사성 분석

## 2. 데이터 접근 및 수집 방식

### 2.1 API 접근 경로

원티드의 채용공고 목록 API와 상세 조회 API를 사용하였다.

| 구분 | API 주소 | 용도 |
|---|---|---|
| 목록 조회 | `https://www.wanted.co.kr/api/v4/jobs` | 카테고리별 공고 ID 수집 |
| 상세 조회 | `https://www.wanted.co.kr/api/v4/jobs/{jid}` | 공고별 상세 정보 수집 |

목록 API에서는 공고 ID를 수집하고, 상세 API에서는 해당 ID를 이용하여 자격요건, 주요업무, 우대사항 등 분석에 필요한 정보를 가져왔다.

API 요청에는 Python의 `requests` 라이브러리를 사용하였으며, 별도의 인증키 없이 요청하도록 구현하였다.

### 2.2 수집 카테고리

원티드에서 제공하는 `tag_type_id`를 이용하여 5개 직무 카테고리의 채용공고를 수집하였다.

| 수집 카테고리 | tag_type_id | 목록 조회 건수 |
|---|---:|---:|
| 데이터 분석가 | 656 | 115건 |
| 데이터 엔지니어 | 655 | 316건 |
| 데이터 사이언티스트 | 1024 | 215건 |
| 백엔드 개발자 | 674 | 400건 |
| 프론트엔드 개발자 | 669 | 355건 |

동일한 채용공고가 여러 카테고리에 포함될 수 있으므로, 카테고리별 조회 건수를 단순 합산하지 않고 `job_id`를 기준으로 중복을 제거하였다.

또한 원티드의 수집 카테고리는 최종 분석 직무와 동일하지 않으므로, 이후 공고 제목을 기준으로 직무를 재분류하였다.

### 2.3 페이지네이션

목록 API에서 한 번에 최대 100건의 공고를 조회하도록 설정하였다.

- `limit`: 100
- `offset`: 0부터 100씩 증가
- 카테고리별 수집 상한: 400건
- 정렬 기준: 최신 공고 순서(`job.latest_order`)

API 응답에서 다음 페이지가 존재하지 않거나 조회 결과가 비어 있으면 해당 카테고리의 수집을 종료하도록 구현하였다.

### 2.4 API 요청 실패 처리

네트워크 오류나 정상적이지 않은 HTTP 응답에 대비하여 다음과 같은 재시도 로직을 구현하였다.

- 요청 제한 시간: 15초
- 최대 재시도 횟수: 3회
- 요청 간 기본 대기 시간: 0.35초
- 재시도 방식: 지수 백오프와 랜덤 지터 적용

요청 실패 시 대기 시간을 점차 늘려 재시도하며, 최종적으로 실패하면 해당 요청을 건너뛰도록 설계하였다.

실제 수집 실행 로그에서는 상세 공고 1,273건 모두 수집에 성공하였으며, 최종 실패 건수는 0건이었다.

### 2.5 상세 데이터 캐시

이미 수집한 공고의 상세 정보를 반복해서 요청하지 않도록 JSON 캐시를 사용하였다.

- 캐시 저장 경로: `data/raw/details/`
- 파일명: `{job_id}.json`
- 저장 형식: JSON
- 동작 방식: 캐시 파일이 있으면 재사용하고, 없거나 읽기에 실패하면 API를 다시 요청

최초 수집 당시 캐시된 상세 공고는 0건이었으며, 이후 수집한 상세 응답을 공고 ID별 JSON 파일로 저장하였다.

## 4. SQLite 데이터베이스 적재

### 4.1 데이터베이스 구성

수집한 CSV를 SQLite 데이터베이스에 저장하여 후속 전처리와 분석에서 활용하였다.

- 데이터베이스 경로: `data/jobs.db`
- 메인 테이블: `jobs`
- 적재 이력 테이블: `build_log`
- 기본키: `job_id`
- 인덱스: `category_id`에 대한 `ix_jobs_cat`

`jobs` 테이블에는 원본 CSV의 15개 컬럼을 저장한다.

`build_log` 테이블에는 DB 적재 시각, 입력 행 수, 신규 등록 건수, 기존 데이터 교체 건수 및 원본 파일명을 기록한다.

### 4.2 DB 적재 전 검증

`build_db.py`에서는 CSV를 불러온 뒤 다음 항목을 확인한다.

- 원본 CSV 파일 존재 여부
- DB 저장에 필요한 필수 컬럼 존재 여부
- `job_id` 결측 여부
- `job_id` 기준 중복 여부
- 같은 회사가 같은 제목으로 다시 올린 공고(회사 + 제목 기준 중복) 여부

`job_id`가 없는 행은 제거하며, 동일한 `job_id`가 중복된 경우 마지막 행을 유지하도록 구현하였다.

`job_id`는 고유하지만 같은 회사가 같은 제목으로 다시 올린 공고는 `job_id`가 달라 위 검사로 걸러지지 않는다. 이런 재게시 공고는 `job_id`가 가장 큰 최신 공고만 남기고, 제거한 공고의 `job_id`를 로그로 출력한다.

실제 적재 로그에서는 CSV 1,273행 중 `job_id` 중복이 0건, 회사와 제목이 같은 재게시 공고가 6건으로 확인되어 1,267행을 적재하였다.

### 4.3 INSERT OR REPLACE 방식

데이터베이스 적재에는 SQLite의 `INSERT OR REPLACE` 구문을 사용하였다.

- 신규 공고: 새로운 `job_id`를 가진 행을 추가
- 기존 공고: 동일한 `job_id`가 존재하면 기존 행을 새로운 데이터로 교체
- 신규/교체 건수: 저장 전에 기존 `job_id`를 조회하여 구분

이는 기존 행의 일부 컬럼만 수정하는 일반적인 `UPDATE`와 달리, 기본키 충돌 시 기존 행을 교체하는 방식이다.

이러한 구조를 통해 동일한 데이터를 다시 적재하더라도 중복 공고가 누적되지 않도록 하였다.

다만 `INSERT OR REPLACE`는 기존 행을 삭제하지 못한다. 중복 기준이 바뀌어 이번 적재 대상에서 빠진 공고가 이전 실행으로 DB에 남아 있으면 분석에 섞이게 되므로, 적재 직후 이번 적재 대상이 아닌 기존 행을 삭제하는 정리 단계를 두었다.

### 4.4 DB 적재 실행 결과

| 항목 | 결과 |
|---|---:|
| CSV 입력 행 수 | 1,273건 |
| `job_id` 중복 공고 | 0건 |
| 회사 + 제목 재게시 공고 제거 | 6건 |
| 적재 후 DB 전체 공고 | 1,267건 |
| 자격요건 결측 | 0건 |
| 최소 요구 경력 범위 | 0~20년 |

재게시 공고를 제거한 뒤 DB에는 1,267건의 공고가 저장되었다.

또한 동일한 데이터를 다시 적재한 후에도 DB 전체 공고 수가 1,267건으로 유지되는 것을 확인하였다. 적재 결과는 `outputs/logs/build_db.txt`에 저장된다.

## 5. 분석 대상 선정 및 기술 추출

### 5.1 직무 재분류

수집 단계에서 사용한 원티드 카테고리는 최종 분석 직무와 다를 수 있으므로, 공고 제목을 기준으로 직무를 재분류하였다.

최종 분석 대상은 다음과 같다.

| 직무 | 분석 공고 수 |
|---|---:|
| 데이터 분석가 | 71건 |
| 데이터 엔지니어 | 92건 |
| 데이터 사이언티스트 | 155건 |
| 백엔드 | 227건 |
| 프론트엔드 | 160건 |
| **합계** | **705건** |

재게시 공고를 정리한 1,267건 중 705건을 최종 분석 대상으로 사용하였다. 나머지 562건은 풀스택 공고 86건과 5개 직무에 해당하지 않는 공고 476건이며 분석 대상에서 제외하였다.

풀스택 공고는 프론트엔드와 백엔드의 기술이 섞여 어느 한 직무의 결과를 왜곡할 수 있어 별도 라벨로 분리하였다. 제외된 공고 중 분석 대상이 섞여 있는지는 무작위 표본 점검으로 확인하고 분류 규칙을 보강하였으며, 자세한 과정은 [분석 보고서](analysis_report.md)의 2.3에 정리하였다.

### 5.2 기술명 추출

채용공고의 텍스트에서 기술명을 추출하기 위해 스킬 사전을 활용하였다.

- 표준 기술명: 90개
- 기술명 별칭: 211개
- 추출 결과: 공고별 기술 등장 여부를 0과 1로 표현

기술명의 다양한 표현을 표준 기술명으로 통합하여 직무별 기술 등장률과 기술 간 관계를 분석하였다.

사전의 별칭이 다른 단어 안의 글자를 잡거나 대문자 표기를 놓치는 문제를 표본 점검으로 확인하고 수정하였다. 수정 내용과 전후 비교는 [분석 보고서](analysis_report.md)의 2.3에 정리하였다.

### 5.3 스킬 매트릭스

최종 분석에 사용한 스킬 매트릭스는 다음과 같다.

- 행: 705개 채용공고
- 기술 컬럼: 90개
- 직무 구분 컬럼: 1개
- 전체 크기: 705행 × 91열

공고당 평균 추출 기술 수는 7.0개, 중앙값은 6개였으며, 기술이 추출되지 않은 공고는 16건(2.3%)이었다.

### 6.2 Git 추적 제외 설정

프로젝트의 `.gitignore`에는 다음 항목이 등록되어 있다.

```gitignore
data/raw/details/
data/raw/wanted_jobs.csv
data/jobs.db
src/__pycache__/
analysis/__pycache__/
```

따라서 원본 CSV, 상세 JSON 캐시, SQLite DB 및 Python 캐시 파일은 새로 Git 추적 대상에 추가되지 않도록 설정하였다.

단, `.gitignore`는 이미 Git이 추적하고 있는 파일을 자동으로 추적 해제하지 않으므로, 실제 공개 여부는 저장소의 추적 상태를 별도로 확인해야 한다. 이 프로젝트에서는 초기 수집 커밋에 원본 데이터가 포함되었다가 나중에 추적만 해제되어 Git 이력에 남아 있었으며, 이를 이력에서 제거하였다(6.4 참고).

### 6.3 원본 데이터 공유 시 주의사항

원본 채용공고에는 외부 플랫폼에서 제공한 정보가 포함되어 있으므로, 원본 데이터의 공개 및 재배포 여부는 해당 서비스의 이용약관과 정책을 확인하여 판단해야 한다.

본 프로젝트에서는 원본 데이터와 분석 코드 및 결과물을 구분하여 관리하도록 구성하였다. 이용약관과 robots.txt를 확인한 결과는 7.4에 정리하였다.

- 정리 전후로 커밋 46개의 메시지와 순서가 유지되고, `data/`를 제외한 모든 파일의 내용이 같은지 비교하여 확인하였다.
- 정리 후 이력에서 `data/` 경로를 가진 커밋과 객체가 없는 것을 확인하였다.
- 이력에서 제거된 이전 커밋은 GitHub 서버에 한동안 남을 수 있어, GitHub Support에 캐시된 화면 제거와 서버의 사용되지 않는 객체 정리를 요청하였다.

**한계:** 이력을 정리하기 전에 저장소를 복제하거나 포크한 사본은 회수할 수 없다. 확인 시점에 포크는 0개, 풀 리퀘스트는 0개였다.

## 7. 재현성 및 데이터 접근의 한계

### 7.1 데이터 수집의 재현성

데이터 수집 코드는 `src/collect_wanted.py`에 구현되어 있으며, 수집 방법을 기록하기 위해 공개한 것이다. 원티드의 robots.txt 사본과 이용약관을 고려하면 재수집은 권하지 않으며, 실행하려면 원티드의 허락을 먼저 확인해야 한다(7.4 참고).

원본 CSV가 준비된 환경에서는 다음 명령어로 SQLite 데이터베이스에 적재할 수 있다.

```bash
python src/build_db.py
```

원본 데이터와 DB가 준비된 환경에서는 다음 명령어로 자체 테스트부터 DB 적재, 직무 분류, 분석 5개까지 한 번에 다시 실행할 수 있으며, 각 단계의 실행 결과는 `outputs/logs/`에 저장된다. 원티드 API를 호출하는 수집은 이 명령어에 포함되지 않는다.

```bash
python run_all.py
```

다만 원본 데이터는 `.gitignore`에 등록되어 있고 Git 이력에서도 제거하였으므로, 저장소를 새로 복제한 환경에서는 원본 데이터가 없어 분석을 처음부터 다시 실행할 수 없다. 대신 분석 결과(`models/`, `outputs/`)와 실행 로그(`outputs/logs/`)를 공개한다.

또한 외부 API의 구조나 접근 정책이 변경되면 동일한 코드가 정상적으로 동작하지 않을 수 있다.

### 7.2 데이터의 시점 및 범위

채용공고는 신규 등록, 수정 및 마감에 따라 변동될 수 있다.

따라서 같은 API를 사용하더라도 수집 시점에 따라 공고 수와 내용이 달라질 수 있으며, 동일한 분석 결과가 항상 재현된다고 보장할 수는 없다.

또한 단일 플랫폼에서 수집한 데이터이므로 전체 IT 채용시장의 기술 수요를 대표한다고 보기는 어렵다.

### 7.3 기술 추출 및 분석의 한계

스킬 사전 기반 추출 방식에서는 사전에 등록되지 않은 기술이 누락될 수 있으며, 기술명이 등장했다는 사실만으로 필수 여부나 요구 숙련도를 판단하기 어렵다.

또한 직무 분류 기준이나 스킬 사전의 구성이 달라지면 동일한 채용공고를 사용하더라도 분석 결과가 달라질 수 있다.

따라서 본 데이터는 채용공고에 나타난 직무별 기술 요구 패턴을 탐색하고 비교하기 위한 자료로 활용하는 것이 적절하다.

### 7.4 수집 방식과 이용약관·robots.txt 확인

#### 수집 방식

- 로그인 없이 원티드의 목록 API와 상세 API를 호출하였다. 수집은 2026-09-17에 한 번 수행하였고, 요청 수는 목록 조회 약 17회와 상세 조회 1,273회였다.
- 요청 사이에 최소 0.35초를 기다리고, 실패하면 대기 시간을 늘려 재시도하도록 구현하였다.
- 수집 코드에는 IP를 바꾸거나 Captcha를 우회하는 기능이 없다.
- 요청의 User-Agent는 일반 브라우저 형태인 `Mozilla/5.0`이며, 수집 도구임을 별도로 밝히지 않았다.
- 수집한 원본은 학습과 포트폴리오 목적의 분석에만 사용하였다. 원본 데이터와 DB는 저장소에 올리지 않고, 저장소에는 기술 등장률 같은 집계 결과와 분석 코드만 공개한다.

#### 이용약관 확인

원티드 이용약관(개인회원, 시행 2026-08-06, 수집 시점에 시행 중)에서 관련된 조항은 다음과 같다.

| 조항 | 내용 |
|---|---|
| 제19조 제2항 | 서비스를 이용하여 얻은 정보를 회사의 사전 동의 없이 복사, 복제, 번역, 출판, 방송 기타 방법으로 상업적으로 사용하거나 제3자에게 제공할 수 없다. |
| 제19조 제3항 | 서비스를 기업정보 확인 및 건전한 취업 등 서비스의 고유한 목적 이외의 목적으로 사용해서는 안 되며, 사이트의 정보 및 서비스를 이용한 영리행위를 해서는 안 된다. |
| 제19조 제7항 | 회사의 사전 허락 없이 자동화된 수단(예: 매크로 프로그램, 봇, 스파이더, 스크래퍼 등)을 이용하여 서비스에 게재된 다른 회원의 아이디, 게시물 등을 수집하는 등의 어뷰징 행위를 막기 위한 회사의 기술적 조치를 무력화하는 일체의 행위(예: IP를 지속적으로 바꿔가며 접속하는 행위, Captcha를 우회하는 행위)를 시도하지 않아야 한다. |

- 위 조항은 약관 원문을 요약한 것이며, 조항 전문은 [원티드 이용약관](https://www.wanted.co.kr/terms)에서 확인할 수 있다.
- 확인한 범위에서 약관에는 API 이용 조건이나 채용공고의 저작권 귀속을 직접 정한 조항이 없었다.
- 약관에서 `회원`은 약관에 동의하고 이용 계약을 맺은 개인으로 정의된다. 로그인하지 않고 공개 API에 접근한 경우에 위 조항이 어떻게 적용되는지는 판단하지 않았다.

#### robots.txt 확인

`https://www.wanted.co.kr/robots.txt`는 자동화된 요청(웹 조회 도구와 `curl`)과 일반 브라우저 모두에서 403으로 차단되어, 현재 내용은 직접 확인하지 못하였다. 대신 인터넷 아카이브(Wayback Machine)에 보관된 가장 가까운 사본(2026-02-06, 수집일보다 약 7개월 앞선 시점)을 확인하였으며, 주요 내용은 다음과 같다.

```text
User-Agent: *
Allow: /
Disallow: /api/
Disallow: /sns-api/
Disallow: /login/
...
```

- 사본의 `Disallow: /api/`는 모든 사용자 에이전트에 대해 `/api/` 아래 경로의 자동 수집을 허용하지 않는다는 뜻이다. 이 프로젝트가 호출한 목록 API(`/api/v4/jobs`)와 상세 API(`/api/v4/jobs/{id}`)는 이 경로에 해당한다.
- 따라서 이 프로젝트의 수집은 robots.txt 사본 기준으로 허용되지 않는 경로에 대한 요청이었다.
- robots.txt는 표준(RFC 9309)상 접근 권한을 부여하거나 차단하는 수단이 아니라 크롤러가 따르도록 요청하는 규약이다. 그러나 자동 수집에 대한 사이트의 의사 표시이므로 이를 따르지 않았다는 사실은 그대로 밝힌다.
- 사본은 수집 시점(2026-09-17)의 robots.txt와 같다는 보장이 없으며, 수집 시점의 내용은 확인하지 못하였다.

#### 정리

- 이 문서는 법률 자문이 아니며, 약관과 robots.txt에 대한 최종 판단은 하지 않았다.
- 원본 데이터의 재배포를 피하기 위해 원본은 저장소에서 제외하고 Git 이력에서도 제거하였다(6.4).
- 수집 경로가 robots.txt 사본에서 허용되지 않는 경로이므로, 같은 데이터를 다시 수집하거나 공개 범위를 넓히기 전에는 약관 전문과 robots.txt를 다시 확인하고 필요하면 원티드의 허락을 받아야 한다.
